TOURNAMENT FILE STORAGE
=======================

data/multiplayer/tournament/files.py owns tournament archive storage.
Hosts and country players load one shared, encrypted game snapshot.
Each country key decrypts a small record that contains the shared session key.
Adding country keys does not add copies of the map, images, or country data.
The public spectator key opens a separate spectator snapshot without the shared session key.

Country players receive the complete snapshot before local display restrictions apply.
Tournament fog and private-data restrictions depend on the game client.
Snapshots and player moves use compact JSON. Gzip compression applies before encryption when it reduces the payload size.
The loader also accepts older encrypted JSON without compression.
New compressed files require a game version with gzip decoding support.
Per-country snapshots and compressed snapshot differences are not supported.
Real-time multiplayer continues to filter each recipient's state before transmission.

Each tournament archive stores one turn. Its history field is null.
The loader ignores history in older tournament archives and removes temporary history files.
Province state is stored once, separately from map geometry.
Only terrain.png and id_map.png are embedded. The game rebuilds the political and cores layers.
Country records, messages, and last-turn unit reports remain complete.

Tournament move import
----------------------

Only the tournament host can use Load Moves.
Each rejected file opens a notification with its filename, country name when known, and rejection reason.
Tournament players also receive rejection details when they use Import Turn.
Long rejection details support scrolling.
Unreadable files, invalid keys, malformed data, unauthorized orders, wrong sessions, wrong turns, and duplicate submissions cannot be accepted.
Rejected files do not change host state.

A move from the previous game release requires host review.
The host can convert it. The converted move must then pass every normal check.
Moves from newer or much older versions cannot be accepted. The player must update and export again.
See documentation/data_migrations.txt, TOURNAMENT MOVE VERSIONS.

Numeric differences in matched ground-unit statistics or new production timing and refunds require host review.
The comparison uses the host's current units and scenario settings.
Aircraft statistics remain under host control.
Aircraft cargo statistics also remain under host control.

Older units without stable IDs cannot be compared reliably.
Changed unit forms use different statistics and are excluded from this comparison.
This check does not prove that all submitted statistics or resource changes are valid.

After reading a stat notification, select Accept to import despite the stated risks.
Select Reject or press Escape to keep the move rejected.
Acceptance can import incorrect values or unfair advantages.
The importer reads and validates the file again before acceptance.
All checks for malformed data, permissions, sessions, turns, and duplicates still apply.

Duplicate checks cover all selected files and the associated review callbacks.
Separate imports can replace a country's earlier draft, as before.
The final notification gives accepted, rejected, and overridden counts.
Input adapters read supported fields and complete missing defaults.
See documentation/data_migrations.txt for the input adapters.
These controls do not change real-time multiplayer or local game modes.

UNIT RANGE SETTINGS
===================

Select Edit Unit Stats in Scenario Settings. This button is right of Edit Construction Turns.
The Range category lists bombardment families and aircraft families from the complete unit library.
Bombardment families appear first. Aircraft families follow. Each group uses alphabetical order.
A labeled divider separates the two groups.
Disabled families remain available in this editor.

Bombardment range uses whole tiles. Each family has one range field.
Aircraft range uses whole map pixels. Each family has a starting range and an increase for each level.
Range = start + (level - 1) * increase.
Starting ranges must be positive. The increase can be zero.
The existing mission rules still convert aircraft range into strike, patrol, relocation, and air drop reach.
See documentation/air_stuff.txt for those rules.

Select Save All Changes to apply the draft. Back discards the draft.
Reset to Defaults restores and saves the library ranges after confirmation.
The Edit Unit Stats button shows ! when saved ranges differ from defaults.
The main Scenario Settings reset keeps these separate editor settings, as it does for construction turns.

Scenario settings store changed fields in unit_range_overrides, keyed by unit family.
Supported fields are bombard_range, air_range_start, and air_range_per_level.
data/queries/unit_info.py validates and applies these fields when the map loads.
Missing or invalid fields use library defaults. Existing saves retain their own scenario settings.
Current defaults come from data/json/unit_data.json and the shared bombardment rules.
See data/generators/recipes.py and data/constants.py for source tuning.

Combat, AI, command validation, and previews read the same active unit library.
Saves and both multiplayer systems retain the host's range settings.
Only scenario setup can change ranges. Player move files and real-time player commands cannot change them.
Real-time lobby edits update the server's ranges before it sends new snapshots.
These settings apply to all local player modes, AI countries, and map editor units.

CONSTRUCTION TURN SETTINGS
==========================

Open the Construction Turns Editor from Scenario Settings.
Both scenario editors show a unit or building image before each family name.
Images follow Settings > Unit Art and use the first library entry for each family.
Administrative actions and conversions have no images.
Images are prepared when the editor opens. Scrolling and drawing reuse them.

The Conversions category has sliders for Truck / Ship Conversion and Air Drop Recovery.
Each slider accepts whole turns from 1 to 9. These actions remain enabled.
The truck and ship directions use the same duration.
See documentation/air_stuff.txt for recovery timing and restrictions.

Scenario settings store nondefault values in conversion_turn_overrides, keyed by the editor's action names.
data/queries/economy.py owns the defaults, limits, and conversion-order helpers.
Older saves without these overrides use the constants in data/constants.py.
Saved games and multiplayer snapshots retain the scenario settings.
Only scenario setup changes these settings. Player move files cannot change the host's durations.
Pending orders retain their remaining turns.
The map editor's direct unit converter changes starting forms immediately.

REGULAR SAVE HISTORY
====================

data/map/history_io.py owns disk history storage.
history.json.gz contains compact JSON compressed with gzip.
The writer compares compressed full snapshots with compressed snapshot changes. It stores the smaller file.
Snapshot changes use the gd5-history-delta-v1 format identifier.
In that format, the first entry contains a complete snapshot. Later entries contain changes from the previous entry.
Dictionary changes preserve deletions and key order. List changes preserve edits, additions, and removals.
Snapshot changes omit unchanged messages, images, research, and units.
The reader restores separate, complete snapshots for the timeline and historical loading.
This format reduces disk storage. It does not reduce the full timeline's memory use.

Older plain history.json files and compressed full snapshots remain readable.
Saving an older game selects the smaller representation. No turns or messages are removed.
Delta history files require a game version with delta decoding support.
Regular metadata and map_data.json remain readable JSON.
Real-time commands and state filtering do not change. Real-time host saves use the same history writer.

BUILDING OUTPUT RESEARCH
========================

data/json/research_template.json defines building output upgrades in building_output_bonuses.
data/generators/recipes.py defines the matching generation recipes.

Each bonus selects building_families, building_groups, or both. Either selector can match a building.
Family names come from queries.get_base_item_name. Group names come from data/json/building_data.json.
The outputs dictionary maps materials, manpower, or fuel to a fractional increase per completed research level.
The optional flat_outputs dictionary adds a fixed amount per completed research level.
Oil production uses the fuel resource key.

Example bonus: {"building_groups": ["recruitment"], "outputs": {"manpower": 0.5, "fuel": 0.25}}.
This example increases manpower output by 50% and fuel output by 25% per level for recruitment buildings.
Percentage bonuses do not create output where the building's base output is zero.
Flat bonuses can add output to a resource with zero base output.
Use building_families to select specific families within a group.
Use the existing req, years, max_lvl, cost, and display_name fields for the technology.
Add its timeline row in screens/game/research.py and its PNG image in assets/images.

Add flat bonuses to the building's base output first.
Percentage bonuses multiply that total. Each completed level multiplies the selected output by one plus its fractional increase.
Two 100% bonuses give four times the base output.
Bonuses affect existing buildings, new buildings, and Basic Factory construction yields.
Basic Factory construction yields use a fraction of its completed materials output, including research bonuses.
data/constants.py defines the construction output fractions and stage timing.
Unselected outputs, province yields, and natural resources retain their existing rules.

Territory penalties apply after research bonuses. Round down each building's output after the territory penalty.

data/queries/economy.py owns output modifiers, building yields, province building yields, and bonus descriptions.
Turn income, economy reports, production previews, research details, and AI research valuation use these helpers.
Production previews include the selected province's territory penalty. Research details show output before that penalty.
Presentation caches update when their screens refresh. Frame drawing reads the cached yields.

AI values output upgrades from its existing buildings and construction projects, with territory penalties.
AI also includes completed bonuses when it values building upgrades.
AI values intermediate requirements when they permit the next reachable building research level.
This value includes the cost of both research projects.
Research-only prerequisites can lead through more than one intermediate technology.
Their details list the next research step. AI valuation follows the same prerequisite links.

Completed levels use each country's existing research dictionary. No additional saved bonus state is required.
Missing technology keys count as unresearched. Existing factory levels remain complete without automatic grants of new technologies.

New research selections use the active prerequisites. Existing research projects keep their recorded progress.
Editor grants and removals use the shared prerequisite rules.
Both multiplayer systems retain their existing research commands, host validation, and privacy rules.
Completed buildings without active library entries produce no output.

Research can require an intermediate technology between levels of the same track.
The optional level_reqs dictionary adds requirements from a specified level onward.
Its keys are level numbers stored as strings. Each value uses the same requirement format as req.
Example: "level_reqs": {"2": {"intermediate_tech": 1}} requires intermediate_tech for level 2 and all later levels.

Base req requirements still apply. Intermediate technologies can require an earlier level of the same track.
Read current technology names, dates, prerequisites, and level gates in data/json/research_template.json and data/generators/recipes.py.
Research selection, AI selection, timeline connections, and editor changes use queries.get_tech_requirements.
Research details identify the levels that require an intermediate technology.
Scenario settings that disable technology also remove its requirements from level_reqs.

Older libraries without level_reqs keep their existing requirements.

UNIT IDENTITY METADATA
======================

data/generators/recipes.py generates unit metadata alongside the existing library fields.
data/json/unit_data.json remains the runtime source.
metadata.family and metadata.tier_order identify a unit family and its tier order.
metadata.research identifies the primary research track.
metadata.requirements lists the required technology levels and year conditions.
metadata.recruitment identifies the industry and coastal requirements.
Additional metadata retains existing display labels, art selection, and AI quota categories.

Historical naval units use the same research, coastal production, combat, and transport rules as other ships.
Their metadata connects each ship to its research track.

Carracks, ironclads, pre-dreadnoughts, dreadnoughts, and battleships have numbered upgrades within their existing research tracks.

All recruitable unit identifiers include a level suffix. The first Roman-numbered level uses I.
Single-level families omit that suffix in visible labels. Saved records and action callbacks retain the numbered identifier.
Older unit references convert through the v47 migration. See documentation/data_migrations.txt.

Research dates, level counts, statistics, and costs come from the unit and research libraries.
data/generators/recipes.py defines the generation rules.

Unit and building rows keep their first year, base statistics, level count, and upgrade interval together.
Research reads the same dates and level counts.
See data/generators/TABLE_FORMATTING.md for row formats, options, and generation steps.
Run data/generators/generate_data.py after recipe edits.

Completed research unlocks production and upgrades within the same ship family.
AI and both multiplayer modes use the same metadata and production rules.
Research prerequisites also apply when an editor grants or removes technology.
Existing completed research stays intact. Missing research levels count as unresearched.

Destroyer research requires the final pre-dreadnought level. It does not require dreadnought research.
The generator derives this prerequisite from the pre-dreadnought recipe's level count.
Submarine research still requires dreadnought research.

When you add unit tiers, update their research recipes and regenerate both runtime files.
Keep research level meanings stable. Migrate older unit identifiers when standardization requires a rename.
Older saves retain their completed research and can use additional levels.

data/queries/unit_info.py reads metadata from the active library.
Divisions do not duplicate this library metadata.
Indexes detect library changes, metadata edits, research-year edits, and obsolescence changes.
Library reloads also invalidate art-name caches.
See documentation/data_migrations.txt for libraries without metadata and invalid explicit fields.

============

compilation_scripts/build_manifest.py owns source inventory, dynamic imports, native dependencies, platform exclusions, and runtime JSON defaults.
compilation_scripts/build_support.py owns filtering, staging, empty directories, resets, and build-path checks.
Both modules are safe to import without game or native audio initialization.

Platform builds and browser checks remain separate verification steps.
