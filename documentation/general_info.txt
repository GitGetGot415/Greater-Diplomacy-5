CUSTOM BATTLES
==============

Custom Battle opens Edit Battle for a standalone land battle from the main menu.
Add Friendly and Add Enemy open the searchable unit picker. Each selection adds
one unit at its selected library level. Cancel closes the picker and keeps added units.
Select a roster card and choose Remove to remove that unit. Drag cards within an
army to change deployment order. Scroll long rosters with the wheel, scrollbar,
or by dragging the roster background. Each army supports up to 64 units.
Random replaces both armies with independently chosen groups of three
to five units. The Year slider limits generation to the highest available level
of each land-unit family at or before the selected year, including any additional
research requirements. Units researched five or more years before the selected
year are excluded. The mouse wheel over the Year slider adjusts one year at a
time. Manual unit selection remains unrestricted by the slider.
Select a friendly roster card and choose Control to command that unit. Release
Control restores an entirely automatic battle. The controlled unit is marked
with a yellow arrow. Reordering cards preserves the controlled unit; removing
that unit or generating new armies clears control.
Simulate opens Preview Battle with the same friendly and enemy roster panels as
Edit Battle. The rosters can be scrolled, but unit editing, reordering, control
selection, random generation, and the Year slider are unavailable in the preview.
Preview Battle shows no battlefield and runs no combat. Start opens Actual Battle
on the grass battlefield. Exit returns to Edit Battle so armies can be changed.
W moves the controlled unit forward and S reverses along its facing direction.
A turns left and D turns right. Space fires straight ahead with the same weapon
cooldown as AI units. Holding Space fires again only when the cooldown expires.
Other friendly units and all enemy units use automatic movement and firing.
Tanks and vehicles use rectangles, artillery uses thin rectangles, infantry and
militia use circles, and cavalry uses ovals. Health bars show remaining strength.
Units approach enemies and fire visible projectiles. Health, attack, defense,
speed, bombardment capabilities, and unit labels come from the default unit library.
The prototype converts movement and range to battlefield pixels and uses shared
health-scaled combat damage. Positive damage rounds up to whole health points so
weakening armies can finish a battle. No resources are spent and no campaign state changes.
Pause freezes combat. The Back key toggles pause during combat. Losing focus also
pauses combat. Pausing and leaving combat clear held movement and fire controls.
Exit returns to army setup; Exit from setup returns to the main menu.
Destroying the enemy army wins. Losing the friendly army, including mutual
destruction, loses. Run Again previews fresh armies; Edit Armies returns to setup.
Custom battles are temporary and are not saved, exported, or used in multiplayer.

TOURNAMENT FILE STORAGE
=======================

data/multiplayer/tournament/files.py owns tournament archive storage.
Hosts and country players load one shared, encrypted game snapshot.
Each country key decrypts a small record that contains the shared session key.
Adding country keys does not add copies of the map, images, or country data.
The public spectator key opens a separate spectator snapshot without the shared session key.

Country players receive the complete snapshot before local display restrictions apply.
Tournament fog and private-data restrictions depend on the game client.
Snapshots and player moves use compact JSON. Gzip compression applies before encryption when it reduces the payload size.
The loader also accepts older encrypted JSON without compression.
New compressed files require a game version with gzip decoding support.
Per-country snapshots and compressed snapshot differences are not supported.
Real-time multiplayer continues to filter each recipient's state before transmission.

Each tournament archive stores one turn. Its history field is null.
The loader ignores history in older tournament archives and removes temporary history files.
Province state is stored once, separately from map geometry.
Only terrain.png and id_map.png are embedded. The game rebuilds the political and cores layers.
Country records, messages, and last-turn unit reports remain complete.

Tournament move import
----------------------

Only the tournament host can use Load Moves.
Each rejected file opens a notification with its filename, country name when known, and rejection reason.
Tournament players also receive rejection details when they use Import Turn.
Long rejection details support scrolling.
Unreadable files, invalid keys, malformed data, unauthorized orders, wrong sessions, wrong turns, and duplicate submissions cannot be accepted.
Rejected files do not change host state.

A move from another game version, or without a version stamp, requires host review.
The host can convert it. Moves from every older release convert. The converted move must then pass every normal check.
A move from a newer version cannot be accepted. The player must update the game.
See data/migrations/MIGRATIONS.md, Tournament Moves.

Numeric differences in matched ground-unit statistics or new production timing and refunds require host review.
The comparison uses the host's current units and scenario settings.
A snapshot move's units first receive the active library statistics, so a library change needs no review.
A new order in a snapshot move that the current rules refuse is dropped and refunded. The host reviews the drop.
Aircraft statistics remain under host control.
Aircraft cargo statistics also remain under host control.

Older units without stable IDs cannot be compared reliably.
Changed unit forms use different statistics and are excluded from this comparison.
This check does not prove that all submitted statistics or resource changes are valid.

After reading a stat notification, select Accept to import despite the stated risks.
Select Reject or press Escape to keep the move rejected.
Acceptance can import incorrect values or unfair advantages.
The importer reads and validates the file again before acceptance.
All checks for malformed data, permissions, sessions, turns, and duplicates still apply.

Duplicate checks cover all selected files and the associated review callbacks.
Separate imports can replace a country's earlier draft, as before.
The final notification gives accepted, rejected, and overridden counts.
Input adapters read supported fields and complete missing defaults.
See data/migrations/MIGRATIONS.md for the input adapters.
These controls do not change real-time multiplayer or local game modes.

UNIT RANGE SETTINGS
===================

Select Edit Unit Stats in Scenario Settings.
The Range category lists bombardment families and aircraft families from the complete unit library.
Bombardment families appear first. Aircraft families follow. Each group uses alphabetical order.
A labeled divider separates the two groups.
Disabled families remain available in this editor.

Bombardment range uses whole tiles. Each family has one range field.
Aircraft range uses whole map pixels. Each family has a starting range and an increase for each level.
Range = start + (level - 1) * increase.
Starting ranges must be positive. The increase can be zero.
The existing mission rules still convert aircraft range into strike, patrol, relocation, and air drop reach.
See documentation/air_stuff.txt for those rules.

Select Save All Changes to apply the draft. Back discards the draft.
Reset to Defaults restores and saves the library ranges after confirmation.
The Edit Unit Stats button shows ! when saved ranges differ from defaults.
The main Scenario Settings reset keeps these separate editor settings, as it does for construction turns.

Scenario settings store changed fields in unit_range_overrides, keyed by unit family.
Supported fields are bombard_range, air_range_start, and air_range_per_level.
data/queries/unit_info.py validates and applies these fields when the map loads.
Missing or invalid fields use library defaults. Existing saves retain their own scenario settings.
Current defaults come from data/json/unit_data.json and the shared bombardment rules.
See data/generators/recipes.py and data/constants.py for source tuning.

Combat, AI, command validation, and previews read the same active unit library.
Saves and both multiplayer systems retain the host's range settings.
Only scenario setup can change ranges. Player move files and real-time player commands cannot change them.
Real-time lobby edits update the server's ranges before it sends new snapshots.
These settings apply to all local player modes, AI countries, and map editor units.

REGULAR SAVE HISTORY
====================

data/map/history_io.py owns disk history storage.
history.json.gz contains compact JSON compressed with gzip.
The writer compares compressed full snapshots with compressed snapshot changes. It stores the smaller file.
Snapshot changes use the gd5-history-delta-v1 format identifier.
In that format, the first entry contains a complete snapshot. Later entries contain changes from the previous entry.
Dictionary changes preserve deletions and key order. List changes preserve edits, additions, and removals.
Snapshot changes omit unchanged messages, images, research, and units.
The reader restores separate, complete snapshots for the timeline and historical loading.
This format reduces disk storage. It does not reduce the full timeline's memory use.
The History menu applies only date changes. It does not copy or retain every snapshot.
It still decompresses and parses the history file. Complete snapshots load after the player selects a turn.

Older plain history.json files and compressed full snapshots remain readable.
Saving an older game selects the smaller representation. No turns or messages are removed.
Delta history files require a game version with delta decoding support.
Regular metadata and map_data.json remain readable JSON.
Real-time commands and state filtering do not change. Real-time host saves use the same history writer.

BUILDING OUTPUT RESEARCH
========================

data/json/research_template.json defines building output upgrades in building_output_bonuses.
data/generators/recipes.py defines the matching generation recipes.

Each bonus selects building_families, building_groups, or both. Either selector can match a building.
Family names come from queries.get_base_item_name. Group names come from data/json/building_data.json.
The outputs dictionary maps materials, manpower, or fuel to a fractional increase per completed research level.
The optional flat_outputs dictionary adds a fixed amount per completed research level.
Oil production uses the fuel resource key.

Example bonus: {"building_groups": ["recruitment"], "outputs": {"manpower": 0.5, "fuel": 0.25}}.
This example increases manpower output by 50% and fuel output by 25% per level for recruitment buildings.
Percentage bonuses do not create output where the building's base output is zero.
Flat bonuses can add output to a resource with zero base output.
Use building_families to select specific families within a group.
Use the existing req, years, max_lvl, cost, and display_name fields for the technology.
Add its timeline row in screens/game/research.py and its PNG image in assets/images.

Add flat bonuses to the building's base output first.
Percentage bonuses multiply that total. Each completed level multiplies the selected output by one plus its fractional increase.
Two 100% bonuses give four times the base output.
Bonuses affect existing buildings, new buildings, and Basic Factory construction yields.
Basic Factory construction yields use a fraction of its completed materials output, including research bonuses.
data/constants.py defines the construction output fractions and stage timing.
Unselected outputs, province yields, and natural resources retain their existing rules.

Territory penalties apply after research bonuses. Round down each building's output after the territory penalty.

data/queries/economy.py owns output modifiers, building yields, province building yields, and bonus descriptions.
Turn income, economy reports, production previews, research details, and AI research valuation use these helpers.
Production previews include the selected province's territory penalty. Research details show output before that penalty.
Production building rows compare the current yield of that building chain with its completed replacement; current values and arrows are yellow, and new values are green.
Presentation caches update when their screens refresh. Frame drawing reads the cached yields.

AI values output upgrades from its existing buildings and construction projects, with territory penalties.
AI also includes completed bonuses when it values building upgrades.
AI values intermediate requirements when they permit the next reachable building research level.
This value includes the cost of both research projects.
Research-only prerequisites can lead through more than one intermediate technology.
Their details list the next research step. AI valuation follows the same prerequisite links.

Completed levels use each country's existing research dictionary. No additional saved bonus state is required.
Missing technology keys count as unresearched. Existing factory levels remain complete without automatic grants of new technologies.

New research selections use the active prerequisites. Existing research projects keep their recorded progress.
Editor grants and removals use the shared prerequisite rules.
Both multiplayer systems retain their existing research commands, host validation, and privacy rules.
Completed buildings without active library entries produce no output.

Research can require an intermediate technology between levels of the same track.
The optional level_reqs dictionary adds requirements from a specified level onward.
Its keys are level numbers stored as strings. Each value uses the same requirement format as req.
Example: "level_reqs": {"2": {"intermediate_tech": 1}} requires intermediate_tech for level 2 and all later levels.

Base req requirements still apply. Intermediate technologies can require an earlier level of the same track.
Read current technology names, dates, prerequisites, and level gates in data/json/research_template.json and data/generators/recipes.py.
Research selection, AI selection, timeline connections, and editor changes use queries.get_tech_requirements.
Research details identify the levels that require an intermediate technology.
Scenario settings that disable technology also remove its requirements from level_reqs.

Older libraries without level_reqs keep their existing requirements.

SETTINGS LOADING
================

data/json/starting_defaults.json is the one source of truth for preference and setup defaults.
Its six preference sections use filenames. They cover scenario settings, general settings, albums, shuffle exclusions, the starting song, and portrait selection.
random_setup holds random scenario setup defaults. ai_defaults holds provider fallback settings.
Startup, missing-setting fallbacks, reset controls, and builds read this file.
Python constants expose configured values for existing callers; they do not define separate defaults.
data/io/starting_defaults.py reads this file. Each caller receives a separate copy.
data/io/settings_schema.py owns current JSON keys, aliases, coercion, and serialization. It reads missing-setting defaults from starting_defaults.json.
keybind_io.load_settings_result returns named keybinds and normalized values.
The controller reads that result directly.
load_settings retains its positional result for older callers.
The positional order is an interface contract. Settings files use JSON keys.

To change distribution defaults:
1. Edit data/json/starting_defaults.json with a text editor. Keep all sections and setting keys.
2. Set scenario rules in scenario_settings.json and general preferences in settings_config.json within that file.
3. Set active_albums.json to a list of album folder names. An empty list selects no albums.
4. Set starting_song.json to {"track": "assets/music/Album/Song.ogg"}, using an existing song path.
5. Use {"track": null} for no fixed starting song.
6. Set the portrait's variant, gradient, gradient_strength, gradient_stepped, gradient_bands, and gradient_dithering in hildehrand_choice.json.
7. Set random setup choices in random_setup and provider fallback settings in ai_defaults. Restart the game after changes.

Builds copy these values into their preference files. They exclude the developer's local preferences.
The game uses these defaults when a preference file is missing.
Existing preference files and saved games keep their saved values. Missing preference fields use the configured defaults.
For an installed copy, use game controls or edit the matching preference file to change existing choices.
Reset controls use this file for the settings each control already covers. The general Settings reset does not clear credentials or reset audio.
The Scenario Settings reset preserves the separate editors' settings.
Keep every keyboard action in settings_config.json's keybinds object, using pygame key names or null for an unassigned action.
Random setup clamps configured values to the available countries, maps, and slider limits.
Do not put private API keys in distribution defaults.
Browser builds include the file in their virtual filesystem. Change distributed defaults before building the browser package.

assets/sounds/volumes.json controls sound effect volume and start offsets by filename.
A number sets the volume multiplier. For example, 1.0 uses the original level.
An object can set both values, for example: "Info.mp3": {"volume": 1.0, "offset": 0.25}.
The offset is in seconds from the start of the source sound, before the pitch setting applies.

The sound effects volume setting multiplies the configured volume. This file does not control music.
Both values must be finite numbers of zero or greater. Missing volume and offset values use 1.0 and 0.0.
An offset at or past the sound length plays no sound. Restart the game after changes.
The web build converts MP3 effects to OGG. Keep the original MP3 filenames in volumes.json;
the sound loader resolves the converted files while preserving their volume and offset keys.
The Pygame sound loader reports each failed effect and continues loading other effects.

Select Category.wav plays when a control selects a browsing group or country scope.
This includes research and construction tabs, art styles, editor country lists, message contacts, and folders.
Select Sub-Category.wav plays when a control selects an item within a group.
This includes research items, songs, scenarios, saved content, art filters, portraits, events, variables, multiplayer countries, and picker rows.
Map and algorithm choices in Random Scenario setup also use this sound.
Checkbox selection uses the item sound. Confirm buttons retain their action sound.
Automatic selection during screen setup stays silent. Research and unit actions retain their specific sounds.
Paper.wav plays when Credits, Assets, Mods, or Translate opens from the main menu.
It also plays for Identity and Claims on the map, and Metadata in the map editor.
Add Contact in Messages also plays Paper.wav.
Puppets.wav plays when Puppets opens from the map.
Send Message.mp3 plays when text is queued in Messages or a trade offer is sent or updated.
Empty text and invalid trade offers do not play this sound. Opening the trade editor does not play it.
Delete Message.mp3 plays when a queued text message or trade offer is deleted in Messages.
The trade editor's Cancel Offer button also plays it when an offer is removed.

BUILD POLICY
============

compilation_scripts/build_manifest.py owns source inventory, dynamic imports, native dependencies, platform exclusions, and the distribution defaults declaration.
compilation_scripts/build_support.py owns filtering, staging, empty directories, resets, and build-path checks.
Runtime preference values come from data/json/starting_defaults.json. See SETTINGS LOADING for editing instructions.
Both modules are safe to import without game or native audio initialization.
Platform entry points retain their packaging tools and native archive procedures.

Windows retains explicit PyInstaller hidden imports.
macOS retains explicit py2app packages, the tkinter recipe workaround, and the ditto archive procedure.
Desktop packages retain loose source copies for the existing source-replacement loader.
Web retains libdragoman.so, the HTML template, and staged audio conversion.
MP3 music and effects require imageio-ffmpeg at build time. Install it with python -m pip install imageio-ffmpeg.
Missing conversion tools or a failed audio conversion stop the build rather than packaging silent MP3 files.
Build the browser package with compilation_scripts/html_compilation.py before testing.
The test_web_build.bat and test_web_build.sh launchers use the same Python helper.
The browser opens after pygbag serves HTTP successfully. Startup failure stops the wait.
On Windows, closing the launcher stops the server's entire process tree, including child Python processes.
Running the launcher again replaces its previous server for the same checkout. Other programs using port 8000 are left running.
Servers started by older launchers must be stopped once manually because those processes have no owned Windows job.
After source changes, rebuild the browser package to refresh the staged game code.
Native and web audio filters retain their separate replacement rules.
On web, text that Python sends to JavaScript must be ASCII. pygbag delivers each UTF-8 byte of any other character as a separate character.
Pass JavaScript source through browser_js_source in data/platform.py before platform.window.eval. Send data as json.dumps output, which escapes non-ASCII characters.
Each asset inventory checks Git ignore rules in one batch. A new inventory reads the rules again.
Distributed saves and mods remain empty. Builds replace local preferences with distribution defaults and exclude editor scratch scenarios.

tests/test_build_manifest.py compares manifest declarations with independent repository scans.
It also checks actual staging with temporary directories.
Tournament rule tests use fast password derivation from tests/tournament_fixtures.py. Archive encryption tests retain production password derivation.
Platform builds and browser checks remain separate verification steps.

MUSIC PLAYBACK
==============

Desktop startup music begins after the first rendered frame is displayed.
Browser startup music waits for the first mouse click or key press.

DISPLAY SUPPORT
===============

Game and map creation, saved games, selected history turns, the history list,
and loading a folder in the map editor use the shared loading overlay.
The bar shows completed loading stages / total stages and advances after each stage finishes.
Its fill stays still while a stage runs. Nested loads contribute to the same total.
Desktop loading runs in a worker while the main loop handles the display.
Browser loading returns to the main loop between stages, including map layers.
A single large file read, procedural generation, or layer can still pause a browser stage.
Loading blocks other actions until it finishes or reports an error.

Turn loading shows separate letter, strategy, movement-order, proactive diplomacy,
response, and map-refresh bars.
Movement progress counts AI countries after their planning passes finish.
An unknown model workload shows Calculating... until its queue is built.
A phase with no work shows a completed gray bar labeled N/A, including an unused letter phase.
The letter bar counts the countries that write letters this turn.
Turning the LLM off leaves rule-based strategy and movement progress active.

ui/bars/ui_bars.py creates display surfaces through set_display_mode.
Game startup, fullscreen changes, and standalone tools use this helper.
On macOS, the helper sets SDL_FRAMEBUFFER_ACCELERATION to "opengl" before it creates the window.
The default Metal window surface has an alpha channel, and most blits set that alpha to zero.
pygame reads zero destination alpha as transparent.
Faded icons then draw at full strength, and copies of the display show text as black boxes.
The OpenGL window surface has no alpha channel, as on Windows.
The helper also disables destination alpha blending on the window surface.
Zero destination alpha can make transparent text backgrounds appear white.
Text and image surfaces keep their transparency when drawn onto the opaque display.
On Apple Silicon, pygame.transform.grayscale damages pixel alpha. get_symbol restores the source alpha after it.

Dragging a scrollable list's content down pulls that content down and moves its scrollbar handle up.
Dragging horizontal content right pulls it right. This rule also applies to map information panels.
Mouse wheel controls and scrollbar dragging retain their existing directions.

Scrolling checkerboard buffers store red, green, and blue (RGB) values without a pixel-alpha channel.
Fractional scrolling and overlay opacity use whole-surface alpha.
These buffers do not inherit pixel alpha from the macOS display.

ui/rendering/symbol_loader.py caches symbol-name results and scaled images.
ui/rendering/overlay_renderer.py caches complete unit-box images in UNIT_BOXES.
Treat shared cached images as read-only.
Pass alpha to get_symbol instead of changing a shared image's alpha.
Map culling checks both width and height.
These caches reduce repeated work when many units use the same image.

ui/widgets/flag_icons.py caches small national flags for country lists and combat rows.
draw_panes(foregrounds=) in ui/widgets/scroll_panes.py draws row flags and stat icons.
ui/bars/ui_bars.py draws its shared textured bar.
screens/game/map_input.py uses the same rectangle to block clicks through the bar.

HELP CONTENT
============

The Help window opens over the map for a fresh game and from the map's Help button.
data/json/tutorial.json holds its text. ui/dialogs/message_box.py reads, checks, and draws it.
Restart the game after editing the file. A malformed file raises an error that names the field to correct.

The file contains a list of categories. Each category has a title, an optional icon, and a list of topics.
Each topic has a title, an optional subtitle, and a list of blocks. Blocks stack from top to bottom.
Icon names come from ui_elements.UI_ICONS, which main.py fills at startup.

Block types:
- text: a paragraph. Set "align" to "center" to center its lines. The default is "left".
- steps: items with a heading and text. An item with an "icon" shows that icon; other items show their number.
  Set "columns" to 2 to fill two columns, top to bottom.
- mouse_buttons: columns that each show an image from assets/mouse, a heading, and caption lines.
- key_box: a recessed strip with a heading and text, for keyboard controls.

A topic taller than its area scrolls with the mouse wheel and a scrollbar.
The category list shows every category, with the open category's topics below it. Keep it within the list's height.
tests/test_help_tutorial.py checks the list height, icon names, and mouse images of the shipped file.

Text in text blocks, step items, mouse captions, and key boxes can contain image markers.
Use [icon:naval:18] to include a naval icon in the text.
Change 18 to set the maximum image dimension in pixels.
Omit :18 to use the text height.
Images keep their original proportions. Images stay with the preceding word when lines wrap.

.gitignore excludes *.json. Add a new file in data/json to Git with git add -f, as the other data/json files were.
